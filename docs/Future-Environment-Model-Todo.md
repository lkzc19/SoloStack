---

## 1. 为什么不进入当前版本

多环境不是单点缺陷修复，而是会改变以下核心契约：

- 数据根目录结构。
- 组件实例的身份。
- Tauri 命令参数。
- 生命周期状态机。
- 启停与切换流程。
- 日志、配置、下载缓存和数据目录定位。
- 前端导航与状态模型。

如果和当前运行时可靠性修复混在一起，会导致：

- 锁、取消和进程接口同时适应两套身份模型。
- 配置写入和目录迁移互相耦合。
- 测试矩阵不可控。
- 每次讨论“实例”都要重新确认是否包含环境维度。

因此当前分支只修复现有模型下的可靠性问题，多环境单独设计、单独实施。

## 2. 目标产品模型

### 2.1 核心约束

- [ ] 一个环境只包含一个组件实例，即固定的 `component + version`。
- [ ] 同一环境不能同时安装 Hadoop 和 Kafka。
- [ ] 同一环境不能安装同组件的两个版本。
- [ ] 不同环境的数据完全隔离。
- [ ] 任一时刻只允许一个活动环境。
- [ ] 切换环境前，旧环境中的组件必须全部停止。
- [ ] 旧环境停止失败时中止切换，活动环境保持不变。

### 2.2 环境定义

每个环境至少包含：

```text
environment_id
name
component
version
created_at
last_activated_at
```

环境 ID、名称和组件配置的稳定性规则需要在实施前确定。

## 3. 建议目录模型

每个环境拥有独立根目录：

```text
~/.solostack/
├── app/
│   ├── settings.json
│   ├── environments.json
│   └── log/
└── environments/
    ├── <environment-id-a>/
    │   ├── environment.json
    │   ├── components/
    │   └── var/
    │       ├── data/
    │       ├── log/
    │       ├── run/
    │       └── downloads/
    └── <environment-id-b>/
        ├── environment.json
        ├── components/
        └── var/
```

### 目录职责

- [ ] `app/settings.json`：应用级设置和当前活动环境。
- [ ] `app/environments.json`：环境索引和展示元数据。
- [ ] `environment.json`：环境自身的组件、版本和创建信息。
- [ ] `components/`：当前环境唯一的组件解压目录。
- [ ] `var/data/`：当前环境组件持久数据。
- [ ] `var/log/`：当前环境组件运行日志。
- [ ] `var/run/`：当前环境 PID 等运行记录。
- [ ] `var/downloads/`：当前环境安装包缓存。

### 设计原则

- [ ] 环境内路径可以继续复用现有目录结构，减少组件实现改动。
- [ ] 环境元数据不是组件配置事实源，实际配置仍写官方配置文件。
- [ ] 下载缓存是否跨环境共享需要单独决策，默认按环境隔离。

## 4. 领域模型改造

### [ ] ENV-01：引入 `Environment`

- [ ] 定义环境 ID、名称、组件、版本和生命周期状态。
- [ ] 提供创建、读取、重命名和删除环境的领域 API。
- [ ] 拒绝第二组件或第二版本进入已有环境。
- [ ] 同一组件同一版本的重装定义为修复当前环境。

### [ ] ENV-02：所有生命周期操作按环境定位

以下命令改为接收 `environment_id`：

- [ ] start
- [ ] stop
- [ ] uninstall
- [ ] config read/write
- [ ] logs
- [ ] status
- [ ] WebUI
- [ ] directories

组件名和版本由环境解析，前端不再分别拼接实例身份。

### [ ] ENV-03：活动环境管理

- [ ] 定义“存在活动环境”和“无活动环境”两种状态。
- [ ] 应用启动时恢复上次活动环境。
- [ ] 活动环境不存在或损坏时给出明确错误。
- [ ] 环境选择器只展示元数据，切换必须走完整切换流程。

### [ ] ENV-04：实例锁与取消机制

本项目不在当前单空间模型中单独实现实例锁；锁粒度、环境切换和安装取消必须在多环境身份稳定后一起落地。

- [ ] 按 `environment_id` 建立环境锁。
- [ ] 引入全局环境切换锁。
- [ ] 引入全局安装队列或安装锁。
- [ ] 每个安装任务使用独立 `task_id` 和取消令牌，不共享单个全局标志。
- [ ] 安装、启动、停止、卸载和配置保存共享目标环境锁。
- [ ] 环境切换按确定的锁顺序获取旧环境锁和新环境锁。
- [ ] 锁冲突返回“当前环境正在执行其他操作”，不阻塞 UI。
- [ ] 任务结束、失败、取消和切换失败后必须释放全部锁。

验收标准：

- [ ] 同一环境不能并发执行生命周期操作。
- [ ] 环境切换不能与任何生命周期操作并发。
- [ ] 取消一个安装不会影响另一个安装。
- [ ] 后端是并发控制的权威层，前端按钮禁用只用于交互优化。

## 5. 环境切换状态机

建议流程：

```text
Idle
  → StoppingOldEnvironment
  → VerifyingOldEnvironmentStopped
  → SwitchingActiveEnvironment
  → Idle

任一步失败
  → SwitchFailed
  → 保持旧环境为活动环境
  → 清理新环境启动产生的临时状态
```

改造项：

- [ ] 增加全局环境切换锁。
- [ ] 切换期间拒绝启动、停止、卸载、安装和配置写入。
- [ ] 停止旧环境组件后检查进程与端口状态。
- [ ] 只有确认旧环境全部停止后才更新活动环境。
- [ ] 切换失败可重试，不需要重新创建环境。
- [ ] 明确切换后是否自动启动新环境组件。

## 6. 并发与锁模型

锁模型必须直接建立在环境身份之上：

```text
GlobalSwitchLock
  → EnvironmentLock(old_environment)
  → EnvironmentLock(new_environment)
```

- [ ] 同一环境不能并发执行生命周期操作。
- [ ] 环境切换不能与任何生命周期操作并发。
- [ ] 取消任务仍使用独立 `task_id` 和取消令牌。
- [ ] 环境切换失败后所有锁必须释放。
- [ ] 不使用全局大锁阻塞普通的状态查询。

FIX-02“实例级操作锁与取消机制”随本环境模型一起实现，不在当前可靠性修复分支中单独实现。

## 7. 旧数据迁移

现有布局：

```text
~/.solostack/
├── components/
├── var/
└── app/
```

迁移目标：

- [ ] 把现有组件、配置、日志、PID 和数据归入一个默认环境。
- [ ] 默认环境名称可配置，初始建议使用 `Default`。
- [ ] 迁移过程保留原有下载缓存或按明确策略重新组织。
- [ ] 迁移必须具备幂等性。
- [ ] 任一步失败不能留下半迁移目录。
- [ ] 迁移前生成可回滚备份或使用同级别名迁移。
- [ ] 迁移后旧路径不再被新代码读取。

## 9. 验收标准

- [ ] 可以创建、切换、重命名和删除多个环境。
- [ ] 一个环境只能安装一个组件的一个版本。
- [ ] 环境 A 无法读取或修改环境 B 的组件、配置、日志、PID 和数据。
- [ ] 切换环境前旧环境组件全部停止。
- [ ] 旧环境停止失败时不会切换到新环境。
- [ ] 切换失败后仍可继续管理旧环境。
- [ ] 删除环境不会影响其他环境。
- [ ] 现有安装可迁移到默认环境并继续启动、配置和卸载。
