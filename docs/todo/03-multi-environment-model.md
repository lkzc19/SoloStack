# 03 SoloStack 多环境模型

> 状态：已完成。
> 创建时间：2026-09-14
> 更新时间：2026-09-18
> 定位：记录多环境的产品约束、已实现能力、明确不做项和剩余验证工作。

---

## 1. 背景与范围

多环境用于隔离不同组件组合、配置、运行数据、日志和运行记录。每个环境拥有独立目录，但所有环境共享经过 SHA256 校验的安装包缓存。

SoloStack 是个人使用的本地应用，当前按以下边界设计：

- 同一时间只允许一个活动环境。
- 同一时间只允许一个安装任务。
- 创建环境属于短操作，不额外设计并发创建机制。
- 环境切换保持简单流程，不引入复杂状态机。
- 并发控制以实际使用场景为准，不按商业多用户服务扩展。

## 2. 待决策事项收口与产品决策

原文档中的待确认事项已经全部收口，不再保留未决项：

| 原待决策事项 | 决策结论 |
| --- | --- |
| 环境名称是否允许重名 | 不允许重名，当前实现已按此约束执行 |
| 是否允许“无活动环境” | 不允许；应用始终保证至少一个活动环境 |
| 切换后是否自动启动目标环境组件 | 不自动启动，由用户明确操作 |
| 删除环境时是否只删除注册信息并保留目录 | 不支持；确认后删除整个环境目录 |
| 是否需要环境导入、导出或复制 | 当前版本不支持，未来有真实需求时重新评估 |
| 默认环境名称是否可配置 | 不需要；固定使用“默认环境”，创建后可以重命名 |

其余已确认的产品决策：

| 项目 | 决策 |
| --- | --- |
| 环境 ID | 使用稳定的 8 位 NanoID，只供代码、目录和接口使用；旧 UUID 目录继续兼容读取 |
| 环境名称 | 用户可见，可重命名，不允许重名 |
| 同环境组件约束 | 同一种组件只能安装一个版本 |
| 不同组件组合 | 同一环境可以同时安装 Hadoop、Kafka 等不同组件 |
| 活动环境 | 应用始终保证至少一个活动环境，不提供用户可见的“无活动环境”状态 |
| 环境切换入口 | 只在主页和设置页环境 tab 提供 |
| 安装页环境展示 | 只读展示当前环境，不允许切换 |
| 切换后行为 | 不自动启动目标环境组件，由用户明确操作 |
| 删除环境 | 只能删除非活动环境，确认后删除整个环境目录 |
| 环境复制能力 | 当前版本不支持导入、导出或复制 |
| 默认环境名称 | 固定使用“默认环境”，用户可以重命名 |
| 安装并发 | 全局串行，不支持并行安装 |
| 环境创建并发 | 不做额外锁；前端阻止重复提交即可 |
| 切换状态机 | 只保留当前简单流程，不做阶段状态和进度事件 |
| 锁模型 | 使用当前全局切换屏障加环境操作锁 |

## 3. 环境模型

每个环境的元数据保存在自己的 `environment.json` 中：

```text
environment_id
name
components: [{ component, version, installed_at }]
created_at
updated_at
last_activated_at
```

核心约束：

- [x] `environment_id` 使用稳定 NanoID，只供代码、目录、接口和日志定位使用。
- [x] 旧版 UUID 环境 ID 仍可读取，避免升级后数据不可访问。
- [x] `name` 是用户可见名称，允许重命名；重命名不改变环境 ID，也不移动目录。
- [x] 同一环境中的 `components` 不允许出现两个相同 `component`。
- [x] 环境列表通过扫描 `environments/*/environment.json` 生成，不维护全局环境索引。
- [x] 同一环境中，同一种组件最多只能安装一个版本。
- [x] 同一环境可以同时安装不同类型的组件。
- [x] 不同环境的数据完全隔离。
- [x] 任一时刻只允许一个活动环境。
- [x] 切换环境前，旧环境中的全部组件必须停止运行。
- [x] 旧环境停止失败时中止切换，活动环境保持不变并允许重试。

## 4. 目录模型

```text
~/.solostack/
├── app/
│   ├── settings.json
│   └── log/
├── cache/
│   └── downloads/
└── environments/
    ├── <environment-id-a>/
    │   ├── environment.json
    │   ├── components/
    │   └── var/
    │       ├── data/
    │       ├── log/
    │       └── run/
    └── <environment-id-b>/
        ├── environment.json
        ├── components/
        └── var/
```

目录职责：

- [x] `app/settings.json` 保存应用级设置和当前活动环境 ID。
- [x] `cache/downloads/` 保存所有环境共享的安装包缓存。
- [x] 安装包缓存复用前通过 SHA256 校验。
- [x] `environment.json` 是环境名称、组件清单和创建信息的事实来源。
- [x] `components/` 保存当前环境的组件解压目录。
- [x] `var/data/` 保存当前环境组件持久数据。
- [x] `var/log/` 保存当前环境组件运行日志。
- [x] `var/run/` 保存 PID、进程身份和运行记录。
- [x] 环境元数据不是组件配置的事实来源，实际配置仍写入官方配置文件。
- [x] 共享缓存下载通过全局锁和原子临时文件避免并发写入。

## 5. 已实现能力

### ENV-01：环境领域模型

- [x] 定义环境 ID、用户可见名称、组件集合和时间信息。
- [x] 提供创建、读取、重命名和删除环境的领域 API。
- [x] 拒绝同一组件的第二个实例或第二版本进入已有环境。
- [x] 允许不同组件在同一环境中共存。
- [x] 已安装组件在安装页显示占用状态，必须卸载后才能重新安装。

### ENV-02：按环境定位

以下命令均接收 `environment_id`，组件操作同时接收 `component`：

- [x] start
- [x] stop
- [x] uninstall
- [x] config read/write
- [x] logs
- [x] status
- [x] WebUI
- [x] directories

版本由环境根据 `component` 解析，前端不再分别拼接实例身份。

### ENV-03：活动环境

- [x] 活动环境 ID 存放在 `app/settings.json`。
- [x] 应用启动时恢复上次活动环境。
- [x] 活动环境不存在或损坏时自动选择可用环境，必要时创建默认环境。
- [x] 环境选择器向用户展示环境名称，接口内部传递环境 ID。
- [x] 切换必须走后端完整切换流程，前端不能只修改当前选择。
- [x] 非活动环境中的组件不能启动。

### ENV-04：操作锁与取消

当前实际锁模型：

```text
GlobalEnvironmentSwitchBarrier
  + EnvironmentOperationLock(environment_id)
  + GlobalInstallLock
```

- [x] 按 `environment_id` 建立环境生命周期操作锁。
- [x] 建立全局环境切换锁。
- [x] 建立全局安装锁，同一时间最多执行一个安装任务。
- [x] 安装、启动、停止、卸载和配置保存共享目标环境锁。
- [x] 切换期间拒绝启动、停止、安装、卸载和配置保存。
- [x] 锁冲突立即返回明确错误，不阻塞 UI。
- [x] 任务结束、失败、取消和切换失败后通过 RAII 自动释放全部锁。
- [x] 状态查询不获取全局大锁。

与早期设计相比，当前没有分别获取旧环境和目标环境锁。全局切换屏障会在切换期间拒绝所有普通环境操作，约束更强，也更符合单活动环境模型。

取消机制按当前产品边界保持为全局安装取消，不为单个安装任务设计独立取消令牌。

## 6. 环境切换流程

当前流程：

```text
检查目标环境
  → 获取全局环境切换屏障
  → 停止旧环境全部组件
  → 验证旧环境全部组件已停止
  → 更新活动环境 ID
  → 释放切换屏障
```

- [x] 切换期间拒绝启动、停止、卸载、安装和配置写入。
- [x] 依次停止旧环境中的全部组件。
- [x] 停止后按受管进程身份验证全部组件已停止。
- [x] 只有确认旧环境全部组件停止后才更新活动环境。
- [x] 切换失败时保持旧环境为活动环境，可直接重试。
- [x] 不自动启动目标环境组件。
- [x] 暂不增加复杂切换状态机和进度事件。

## 7. 旧数据迁移

现有旧布局：

```text
~/.solostack/
├── components/
├── var/
└── app/
```

- [x] 把旧组件、配置、日志、PID 和数据归入环境目录。
- [x] 同组件只有一个版本时迁入默认环境。
- [x] 同组件存在多个版本时拆分为独立环境。
- [x] 默认环境固定命名为“默认环境”。
- [x] 旧 `downloads/` 和 `var/downloads/` 合并到共享 `cache/downloads/`。
- [x] 迁移使用 staging 目录，失败时回滚已移动路径。
- [x] 应用启动时恢复异常退出留下的 staging 目录。
- [x] 重复执行迁移时不会重复处理已完成的数据。
- [x] 迁移后新代码不再读取旧组件目录。

验证结果：

- [x] 对迁移流程完成独立的端到端验证。
- [x] 同组件多版本拆分后，每个环境都可以继续保存配置、启动、停止和卸载组件。

## 9. 明确不在当前版本实现

以下内容已评估，不属于当前多环境范围：

- [x] 不做并行安装。
- [x] 不做并行安装的任务级取消令牌；安装日志仍使用 `trace_id` 关联。
- [x] 不做环境创建的后端并发名称锁。
- [x] 不做复杂环境切换状态机和阶段进度事件。
- [x] 不分别获取旧环境和目标环境锁，继续使用当前全局切换屏障。
- [x] 不做环境之间导入、导出或复制。
- [x] 不做可配置的默认环境名称。
- [x] 不支持删除环境时只保留数据目录。
- [x] 不在切换后自动启动目标环境组件。

以上项目只有在未来出现多窗口、外部 API、并行安装或环境迁移共享等真实需求时再重新评估。
